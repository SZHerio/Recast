# Threat Director — спецификация M1

## 1. Граница ответственности

Threat Director отвечает только за внешнюю системную реакцию мира на развитие игрока:

- единый `tech_epoch` P0–P9;
- репутацию `-100…100` отдельно по каждой фракции;
- формальную принадлежность и особые статусы;
- договоры, перемирия, дань и союзные обязательства;
- подтверждённые факты и последствия решений;
- экземпляры фракционных баз B0–B6;
- плановые операции от разведки до восстановления;
- безопасные read models для квестов, NPC и интерфейса.

Он не хранит текст диалога, не управляет оружейной баллистикой, не спавнит природных мобов вместо In Control! и не рисует квестбук.

## 2. Единственный параметр технологического развития

Авторитетный параметр называется:

```text
industrial_frontier:tech_epoch = integer 0..9
```

Он хранится в SavedData на UUID промышленной команды. Одиночный игрок получает персональную команду того же типа. Только это значение разрешает технологические loadout, уровень баз, тип операций, торговые каталоги и эпохальные диалоговые условия.

`tech_epoch`:

- монотонен в обычном прохождении;
- не зависит от числа дней мира;
- не повышается от случайного лута, убийства, посещения измерения или отдельного scoreboard-флага;
- меняется только атомарным `advance_epoch` intent после проверки полного milestone;
- записывает причину, старое/новое значение, team UUID, actor UUID, Build ID и время;
- не может перескочить через эпоху без специальной миграции данных.

`epoch_floor` допустим только как миграционный anti-exploit guard при смене команды. Он не является вторым прогрессом, не разблокирует контент самостоятельно и никогда не показывается сценаристам как условие. Любой игровой gate читает только итоговый `tech_epoch` команды.

Предварительная шкала:

| Значение | Эпоха | Системный смысл |
|---:|---|---|
| 0 | P0 — Выживание и разведка | дерево, камень, ранние лагеря, ручное снабжение |
| 1 | P1 — Металл и поселение | кирпич, ранний металл, укреплённые лагеря |
| 2 | P2 — Пар | котлы, мастерские, простое дальнобойное оружие |
| 3 | P3 — LV | сталь, склады, свет, ранняя электрификация |
| 4 | P4 — MV | химическая промышленность, бетон, радио, постоянные базы |
| 5 | P5 — HV | нефтехимия, бункеры, серийное вооружение, промышленный город |
| 6 | P6 — EV | атомная инфраструктура, броневые блоки, автоматические системы |
| 7 | P7 — IV | композиты, защищённые комплексы, высокоточное вооружение |
| 8 | P8 — Орбита | герметичные базы, стратегическая логистика, космические центры |
| 9 | P9 — Межпланетная система | энергетическая защита и финальные мегапроекты |

## 3. Состояние команды и игрока

Минимальный SavedData:

```text
schema_version
world_id
teams[team_uuid]
  tech_epoch
  members[player_uuid]
  reputation[faction_id]
  affiliation
  special_statuses[]
  treaties{}
  facts{}
  contracts{}
  bases{}
  operations{}
  audit_log[]
players[player_uuid]
  team_uuid
  epoch_floor_guard
  personal_facts{}
definitions_hash
build_id
```

Репутация и принадлежность никогда не объединяются. Игрок может иметь высокое уважение без членства, быть формальным членом при внутреннем недоверии или сохранить особый статус после выхода.

Пороговые названия репутации:

| Диапазон | Статус |
|---:|---|
| `-100…-76` | заклятый враг |
| `-75…-41` | враждебность |
| `-40…-11` | недоверие |
| `-10…10` | нейтралитет |
| `11…40` | уважение |
| `41…75` | союз |
| `76…100` | особый статус |

Изменение репутации требует reason code и ограничивается серверной таблицей. Убийство, торговля или контракт не вызывают произвольную команду из текста NPC.

## 4. Intent API

Внешние системы не получают setter. Они отправляют узкое намерение:

```text
/if_threat intent <type> <definition_id> <nonce>
```

Сервер сам выводит actor, команду, эпоху и контекст. Параметры не содержат командных строк.

Обязательные типы M1–M4:

- `sandbox_ping` — идемпотентная проверка связи;
- `accept_contract` / `decline_contract`;
- `deliver_contract_resource`;
- `report_operation_outcome`;
- `dialogue_choice` с заранее зарегистрированным choice ID;
- `request_treaty`;
- `advance_epoch` — только из milestone adapter;
- `admin_repair` — отдельное разрешение, причина и audit record.

Проверки каждого intent:

1. definition ID существует и разрешён для Build ID;
2. actor имеет право действовать за команду;
3. nonce не использован;
4. эпоха и репутация попадают в диапазон определения;
5. предметы/цель/операция существуют и ещё не обработаны;
6. изменение укладывается в серверные лимиты;
7. результат записывается атомарно;
8. зеркала обновляются только после сохранения.

## 5. Read-only зеркала

Для совместимости допускаются scoreboard objectives:

- `if_epoch`;
- `if_rep_01` … `if_rep_06`;
- `if_affil`;
- `if_threat`.

Они обновляются из SavedData и никогда не читаются обратно. Ручная команда scoreboard может временно изменить цифру на экране, но не меняет состояние и будет перезаписана при следующей синхронизации.

FTB Quests получает только predicates/read results и отправляет intents. Easy NPC читает зеркала для показа ветки, но изменение состояния идёт через intent. TACZ: NPCs получает уже разрешённый `loadout_definition_id`, а не самостоятельно выбирает оружие по дням мира.

## 6. Базы B0–B6

Каждая фракция имеет определения уровней, но конкретный уровень ограничен `tech_epoch` целевой команды:

| Tier | Назначение | Примерный предел эпохи |
|---:|---|---|
| B0 | ранний лагерь | P0 |
| B1 | укреплённый лагерь | P1–P2 |
| B2 | постоянная база | P2–P3 |
| B3 | промышленный аванпост | P3–P5 |
| B4 | военный комплекс | P5–P6 |
| B5 | высокотехнологичный объект | P6–P8 |
| B6 | космический/стратегический центр | P8–P9 |

Фактический tier не превышает таблицу эпохи, даже если миру тысяча дней. Каждая схема проходит функциональный аудит: спальные места, склад, снабжение, мастерская, оружейная, командный пункт, оборона, вход/отступление и поздний источник энергии.

Лут базы ограничивается эпохой и преимущественно состоит из разведданных, чертежей, повреждённых деталей, компонентов, оптики, инструментов, валюты и образцов. Готовое оружие будущей эпохи запрещено.

## 7. Жизненный цикл операции

Операция — не внезапная бесконечная волна. Серверный автомат состояний:

```text
PLANNED
  -> RECON
  -> WARNED | COVERT
  -> NEGOTIATION_WINDOW
  -> PREPARATION
  -> ACTIVE
  -> RESOLVED_SUCCESS | RESOLVED_FAILURE | ABORTED
  -> RECOVERY
  -> COOLDOWN
  -> CLOSED
```

Требования:

- операция имеет конкретную цель и ограничение времени;
- база игрока не разрушается необратимо офлайн;
- союзники могут быть предупреждены;
- переговоры, дань, ложная информация и совместная защита существуют как заранее написанные ветви;
- исход влияет на репутацию/договоры через таблицу, а не произвольный скрипт;
- повторная операция ждёт cooldown;
- после сбоя сервера состояние восстанавливается из SavedData без двойной награды или второго рейда.

## 8. Definition data

Контент хранится отдельно от экземпляров:

- `factions/*.json` — идеология, экономика, архитектура, роли, товары и шкалы;
- `loadouts/*.json` — разрешённые классы оружия/брони по P0–P9;
- `bases/*.json` — B0–B6, палитры, помещения, лут-таблицы;
- `contracts/*.json` — условия, стоимость, сроки, последствия;
- `operations/*.json` — lifecycle, цели, предупреждения, cooldown;
- `dialogue_facts/*.json` — только факты и choice IDs, не генерируемые реплики.

Определения имеют schema version, stable ID, min/max epoch, required/forbidden facts, reputation range и deterministic reward table. Hot reload не меняет уже активный экземпляр без миграции.

## 9. Безопасность и тестирование

- Сервер авторитетен; клиент не передаёт итог репутации или эпохи.
- Любой сетевой пакет валидирует размер, ID, actor и rate limit.
- Nonce предотвращает повторную награду.
- SavedData пишется атомарно и имеет резервную копию перед миграцией.
- Миграция прогоняется на фикстурах минимум двух старых schema versions.
- NPC не исполняет свободный текст как команду.
- Административный repair оставляет неизменяемую audit-запись.
- Нагрузочные тесты 20/40/80 NPC выполняет владелец; Codex анализирует логи, но Minecraft не запускает.

## 10. M1 deliverable

На M1 готовы только этот контракт, JSON Schemas и два примера. Нет JAR, сетевого кода, реальной SavedData, рейдов и диалогов. Это намеренное ограничение: формат состояния фиксируется до контента, а исполняемый мод появится только после CurseForge-публикации и отдельного пользовательского gate.
