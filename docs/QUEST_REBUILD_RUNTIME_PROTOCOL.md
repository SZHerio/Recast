# Игровая приёмка новой квестовой книги

Этот протокол выполняет пользователь. Разработка и статическая проверка не запускают Minecraft/Forge и не выдают игровой результат за подтверждённый.

## Как фиксировать результат

Для каждой проверки запишите:

- профиль или мир;
- одиночная игра либо команда из нескольких игроков;
- stable alias квеста;
- ожидаемое и фактическое условие;
- засчиталась ли задача автоматически;
- виден ли следующий узел и правильно ли проведены линии;
- сколько минут и ручных повторов занял путь;
- снимок экрана и фрагмент `latest.log`, если результат расходится с ожиданием.

Не исправляйте несколько квестов одной командой: иначе будет невозможно понять, какое условие сломано.

## Вертикальный срез Onboarding → P0 → P1

1. Откройте новую книгу без предметов. Главы помощи и onboarding должны быть видны сразу.
2. Проверьте, что onboarding обучает книге, JEI/Jade/JER, команде и восстановлению, но не требует добычи ресурсов.
3. Начните P0. Последовательность должна идти так: бревно → доски → верстак → инструменты/печь/укрытие.
4. Убедитесь, что сундук не требуется раньше верстака, а пакет из четырёх сундуков не блокирует P0.
5. Приготовьте любой один вариант из категории походной еды. Хлеб не должен быть единственным допустимым путём.
6. Найдите по очереди два разных железосодержащих минерала из списка задачи. Каждый должен засчитывать разведку источника; ни один не должен закрывать квест готового металла.
7. Переплавьте подходящее сырьё. Квест продукта должен засчитаться только при получении железного слитка.
8. Завершите все обязательные ветви P0 и commissioning лагеря. До этого P1 закрыт; после этого P1 открыт.
9. Выполните `/if_intent`. Командный `tech_epoch` должен измениться с P0 на P1 ровно один раз.
10. Повторно откройте/перепроверьте commissioning. Эпоха не должна перескочить на P2.

## Командная проверка

1. Создайте команду FTB Teams из двух игроков и убедитесь, что оба видят общий квестовый прогресс.
2. Завершите commissioning одним игроком. Оба участника должны получить сообщение о переходе, а `/if_intent` должен показывать одинаковую эпоху.
3. Один участник выходит и входит снова. Эпоха и прогресс не должны зависеть от имени вошедшего игрока.
4. Игрок покидает команду и создаёт новую. Новая команда не должна наследовать `tech_epoch` старой.
5. Публичный вызов `/kubejs custom_command if_advance_epoch` не должен менять эпоху.
6. Операторская `/if_advance_epoch` используется только в копии тестового мира и должна повышать ровно одну эпоху с записью в журнал.

## Приёмка каждой эпохи P1–P9

Для каждой главы повторяется один и тот же контроль:

- root открывается только commissioning предыдущей эпохи;
- все обязательные ветви видимы и действительно являются предками commissioning;
- `ANY_OF` принимает любой обещанный вариант, а `ALL_OF` требует все названные части;
- действия «поставьте», «используйте», «посетите» и «получите жидкость» не закрываются обычной галочкой;
- учебная партия укладывается в 1–3 запуска, массовый объём появляется только после автоматизации;
- описание механизма совпадает с его GUI, единицами, сторонами ввода/вывода и реальным результатом;
- диагностика помогает устранить хотя бы одну намеренно созданную неисправность;
- commissioning меняет `tech_epoch` ровно на следующий уровень; P9 только отмечает финальное завершение.

## Что считать блокирующей ошибкой

- обязательный квест физически недостижим из открытых рецептов;
- один допустимый материал принимается, а равноценный — нет;
- квест засчитывается предметом, который не доказывает заявленное действие;
- необязательная ветвь тайно блокирует commissioning;
- эпоха меняется без commissioning или дважды от одного события;
- текст обещает существование отключённой машины;
- русский текст содержит непонятную кальку, внутренний ID вместо названия или не объясняет следующий практический шаг;
- ручной повтор превышает hard-limit из `docs/registries/m2_grind_budget.json`.

До устранения блокирующей ошибки соответствующая эпоха остаётся `USER_GATE_FAILED`, даже если все статические валидаторы прошли.
