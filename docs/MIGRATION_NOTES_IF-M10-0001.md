# Миграция на IF-M10-0001

Статус документа: `STATIC_UNTESTED`

Исходный статический срез: `IF-M9-0001`

Целевой срез: `IF-M10-0001`

M10 на момент создания этого документа добавляет релизную дисциплину и не
переименовывает игровые ID, не меняет worldgen и не удаляет контент. Это не
доказывает совместимость будущего итогового M10: любое последующее изменение
модлиста, рецептов, worldgen или SavedData обязано дописать сюда отдельную
миграционную запись.

Minecraft и Forge при составлении заметок не запускались. Все действия ниже
выполняет владелец на копии данных.

## 1. Кому нужна миграция

| Сценарий | Действие |
|---|---|
| Новый игрок | Чистая установка IF-M10; переносить ничего не нужно |
| Существующий мир IF-M9 | Только через резервную копию и отдельный новый instance |
| Мир более раннего M0–M8 | Сначала сохранить его исходный модлист и build ID; прямой прыжок считается непроверенным |
| Сервер | Остановить сервер, сохранить мир и конфиги, затем проверить копию отдельно от production |
| Откат с IF-M10 | Восстановить полный backup, а не открывать уже обновлённый мир старой сборкой |

## 2. Обязательная резервная копия

Перед переносом полностью закройте клиент, сервер и CurseForge App. Резервная
копия должна находиться вне папки рабочего instance и включать:

- весь каталог `saves/<мир>/`, без выборочного копирования region-файлов;
- `level.dat`, `level.dat_old`, `region`, `entities`, `poi`, `playerdata`,
  `advancements`, `stats`, `data` и все каталоги измерений;
- `saves/<мир>/ftbquests/` — командный прогресс книги;
- `saves/<мир>/serverconfig/` — реально действующие настройки этого мира;
- исходные `manifest.json`, `config/`, `defaultconfigs/` и `kubejs/`;
- снимок точного модлиста и хэшей из generated-аудита исходного build;
- для сервера — whitelist, ops, bans и server.properties, если они хранятся
  рядом с сервером.

Папка `backups/` live-instance не является доказательством пригодного backup:
она исключается из релиза, может быть неполной и может принадлежать модовой
системе автоматических копий. Нужен отдельный датированный архив, который
можно восстановить без текущего instance.

Минимальная карточка backup:

```text
Мир:
Исходный build ID:
Дата и время остановки:
Размер архива:
Хэш архива:
Точный mod lock:
Кто создал и где хранится:
```

## 3. Безопасный порядок обновления

1. Создайте backup по разделу 2.
2. Установите IF-M10 в новый пустой CurseForge-instance.
3. Не копируйте в него `mods`, `config` или `options.txt` из старого instance.
4. Убедитесь по launcher-интерфейсу, что все manifest-файлы разрешились.
5. Скопируйте в новый instance только копию выбранного мира.
6. Сначала откройте именно копию. Исходный мир остаётся закрытым.
7. После загрузки проверьте книгу заданий, команду, эпоху, ключевые фабрики,
   измерения, колонию, фракционное состояние и инвентари.
8. Закройте мир штатно, сохраните `latest.log` и заполните тестовую карточку.
9. Только после успешного повторного открытия копии можно принимать решение о
   переносе основного мира.

Старые `config` не копируются целиком, потому что так можно вернуть удалённые
ключи, локальные пользовательские значения и скрыть ошибку release-профиля.

## 4. Мир и генерация

В сборке присутствуют Biomes O' Plenty/TerraBlender, YUNG's worldgen,
структуры, руды GregTech, NuclearCraft/HBM datapack modifiers и космические
измерения. Поэтому действуют правила:

- уже созданные чанки не должны считаться тестом новой генерации;
- новый worldgen появляется только в новых чанках, если конкретный мод не
  предоставляет отдельную безопасную retrogen-механику;
- граница старых и новых чанков может быть визуально заметна;
- удаление biome/worldgen/structure-мода из существующего мира считается
  потенциально разрушительным;
- удаление космического мода запрещено, пока игроки, сущности или контейнеры
  находятся в его измерениях;
- автоматическое удаление region-файлов и «очистка неизвестных блоков» не
  являются штатной миграцией.

Для текущего документального среза M9 -> M10 новый мир не заявлен. Если итоговый
M10 изменит владельца worldgen, перечень модов или dimension ID, поле должно
быть немедленно изменено на `NEW_WORLD_REQUIRED` либо дополнено проверенной
chunk-миграцией.

## 5. Конфиги и их приоритет

У конфигурации есть разные уровни:

- `config/` — общие client/common настройки instance;
- `defaultconfigs/` — шаблон для новых миров;
- `saves/<мир>/serverconfig/` — действующий server-config конкретного старого
  мира;
- `config/paxi/` — авторские datapack/resource-pack Recast;
- `config/ftbquests/quests/` — compiled-определения книги;
- `kubejs/` — авторские рецепты, gates и состояние интеграций.

`defaultconfigs` не обязан переписать `serverconfig` уже существующего мира.
Поэтому после обновления сравниваются значения, а не копируются папки поверх
друг друга. Если новый обязательный ключ отсутствует в world-serverconfig,
его переносится вручную с объяснением. Пользовательские client-настройки
переносятся только после прохождения чистого UI-теста.

Paxi и FTB Quests являются частью авторского контракта и не должны заменяться
старыми копиями. Иначе мир запустится с новым modlist, но со старой прогрессией
или рецептами.

## 6. Квесты и стабильные ID

Авторитетный реестр — `docs/registries/stable_ids.json`. На базовой отметке он
содержит 457 семантических ID и 96 resource ID. `retired_ids.json` пуст.

Правила миграции:

1. Существующий шестнадцатеричный ID никогда не получает новый смысл.
2. Название главы и положение на экране можно менять без смены ID.
3. При разделении квеста старый ID остаётся у наиболее близкого продолжения,
   остальные узлы получают новые ID.
4. Удалённый ID переносится в `retired_ids.json` и никогда не используется
   повторно.
5. Если смысл обязательного условия изменился, нужен явный mapping и решение,
   сохранять ли старое завершение.
6. `config/ftbquests/quests` содержит определения, а
   `saves/<мир>/ftbquests/*.snbt` — прогресс команды. Нельзя подменять одно
   другим.

После загрузки копии проверяются минимум:

- открытые ранее главы остаются открыты;
- завершённые обязательные квесты не сбросились;
- новые квесты не получают completion от чужого старого ID;
- командный прогресс одинаков для членов одной FTB Teams-команды;
- P0–P9 и вспомогательные главы не создают дубликаты.

## 7. Эпоха, фракции и серверное состояние

Текущая исполняемая реализация хранит авторское командное состояние через
KubeJS `server.persistentData`; `if_epoch` и репутационные scoreboard-objective
являются отображением, а не источником истины. В state входят как минимум
`tech_epoch`, репутации, договоры, факты и операции.

Поэтому нельзя переносить только scoreboard командами или вручную выставлять
`if_epoch` как замену миру. Сохраняется весь каталог мира. После миграции
сравниваются:

- технологическая эпоха команды P0–P9;
- шесть значений репутации;
- принадлежность и особые статусы;
- действующие договоры;
- активная операция, её cooldown и защита от двойной награды;
- посещённые/разрешённые базы и сюжетные факты.

Если state не читается, мир не продолжают. Сначала сохраняют лог и копию
повреждённого состояния, затем пишут одноразовую миграцию. «Починка» выдачей
всех квестов или эпохи P9 уничтожает диагностические данные.

## 8. Удаление модов и контента

Удаление делится на четыре класса:

| Класс | Пример | Требование |
|---|---|---|
| Клиентское удобство без world-state | UI/подсказка | Чистый instance-тест; проверить зависимости |
| Рецепты/интеграция | KubeJS addon | Сначала удалить обращения и рецепты, затем зависимость |
| Блоки, предметы, сущности | Технический или мебельный мод | Найти размещённые блоки/инвентари; подготовить замену; проверять копию мира |
| Биомы, структуры, измерения | Worldgen/space | По умолчанию новый мир либо отдельная доказанная миграция |

Нельзя просто убрать JAR и согласиться с предупреждением о missing registry
entries. Целевой документ удаления обязан перечислить:

- удаляемые mod/resource IDs;
- замену блоков, жидкостей, предметов и рецептов;
- влияние на квесты и stable IDs;
- очистку Paxi/KubeJS ссылок;
- переход для машин и складов игрока;
- способ отката и результаты теста на копии.

## 9. Откат

Надёжный откат — восстановление полного датированного backup в отдельный
instance с точным старым mod lock. Открывать мир, уже сохранённый IF-M10, под
IF-M9 без восстановления нельзя: моды могли обновить NBT, capability,
SavedData, serverconfig или DataVersion даже при внешне успешном запуске.

Порядок:

1. Не открывать повреждённую копию повторно.
2. Сохранить её и `latest.log` как материал диагностики.
3. Создать новый instance с точным исходным manifest/mod lock.
4. Восстановить исходный мир из backup.
5. Сверить хэши и открыть только восстановленную копию.
6. Не смешивать старые JAR с новыми config/KubeJS.

## 10. Карточка результата владельца

```text
Исходный build:
Целевой build: IF-M10-0001
Новый instance: да/нет
Использована копия мира: да/нет
Одиночная/сервер:

Проверено:
- мир открылся повторно;
- FTB Quests и FTB Teams;
- tech_epoch и фракционное состояние;
- фабрики/контейнеры/трубы;
- колония и NPC;
- Overworld/Nether/End/космические измерения;
- новые чанки;

Найденные пропажи или сбросы:
latest.log:
Решение: принять / исправить / откатить
```

До возврата этой карточки совместимость существующих миров остаётся
`OWNER_GATE_PENDING`.
